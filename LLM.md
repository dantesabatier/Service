# LLM Agents

Service includes a provider-neutral agent runtime for applications that extend the generated REST foundation with agentic behavior. `LLMAgent` coordinates model turns, tool calls, budgets, context assembly, optional retrieval and telemetry; the application supplies the provider client, tool catalogue and policy.

This API is separate from the `/mcp` server. An agent can execute the same catalogue in-process through `ToolRegistry`, or connect to a remote MCP server through `MCPToolExecutor`.

## First run

The smallest useful run needs a provider client, a tool registry and at least one user message. Provider endpoints, models and keys are application configuration; the framework does not read them from `.env` automatically.

```php
use Sabatier\Foundation\ArrayClass;
use Sabatier\Foundation\URL;
use Sabatier\Service\LLM\AnthropicClient;
use Sabatier\Service\LLM\LLMAgent;
use Sabatier\Service\LLM\LLMMessage;
use Sabatier\Service\LLM\LLMMessageRole;
use Sabatier\Service\MCP\Tools\ToolRegistry;

/** @var ToolRegistry $registry */
$client = new AnthropicClient(
    model: $model,
    endpoint: new URL($providerEndpoint),
    key: $apiKey,
);

$agent = new LLMAgent(
    $client,
    $registry,
    canSpawnSubagents: false,
    timeLimit: 30.0,
);

$history = new ArrayClass([
    new LLMMessage(LLMMessageRole::user, "Summarize the open orders."),
]);
$run = $agent->run($history, "Use tools for facts. Do not invent records.");

if (!$run->isComplete) {
    throw new RuntimeException("Agent stopped: {$run->stopReason->value}");
}

$answer = $run->messages->last?->content;
```

`LLMAgent::run()` clones the input history and returns only messages generated by that invocation. Append those messages to the application's stored conversation before the next run. The returned `LLMRun` also carries cumulative `inputTokens`, `outputTokens`, `toolCallResults`, `stopReason`, `isRetryable` and the derived `isComplete` flag.

## Choosing an orchestration loop

`ReActLLMAgentLoop` is the default model → tools → results cycle. `PlanExecuteLLMAgentLoop` adds an explicit planning gate: the model sees the real catalogue while planning, but a real call made before a valid `submit_plan` call is returned as a correctable tool error without reaching the executor. A direct answer that needs no tool may still complete immediately, and an accepted plan may be revised as new evidence arrives.

```php
use Sabatier\Service\LLM\PlanExecuteLLMAgentLoop;

$agent = new LLMAgent(
    $client,
    $registry,
    canSpawnSubagents: false,
    timeLimit: 30.0,
    loop: new PlanExecuteLLMAgentLoop(),
);
```

Both loops run through the same `LLMAgentSession`. Planning calls, rejected early calls and real executions consume the shared tool budget, produce ordinary tool-result messages and emit the same structured spans. A strategy cannot append messages directly, bypass write approval or construct its own `LLMRun`.

Framework and application loop implementations can extend `Sabatier\Service\Testing\LLMAgentLoopConformanceTestCase` in their PHPUnit suite. This optional namespace ships with the Composer package but is loaded only by tests. The reusable contract drives the loop through the real runtime and checks direct completion, a guarded tool round trip, the iteration cap and write approval:

```php
use Sabatier\Service\Testing\LLMAgentLoopConformanceTestCase;

final class DomainLoopConformanceTest extends LLMAgentLoopConformanceTestCase
{
    protected function loop(): LLMAgentLoop
    {
        return new DomainLoop();
    }
}
```

## Provider clients

All clients normalize provider responses into `LLMTurn` and share timeout and retry controls from `LLMClient`.

| Client | Wire API | Authentication |
|--------|----------|----------------|
| `StandardLLMClient` | OpenAI-compatible Chat Completions | `Authorization: Bearer` |
| `AnthropicClient` | Anthropic Messages | `x-api-key` |
| `OllamaClient` | Native Ollama `/api/chat` | Optional bearer token |

Each constructor accepts `model`, `endpoint` and `key`. `endpoint` must identify the complete provider operation, not only its host. Provider-specific body fields can be assigned through `extraBody`:

```php
use Sabatier\Foundation\Dictionary;

$client->extraBody = new Dictionary([
    "temperature" => 0.2,
]);
$client->timeoutIntervalForRequest = 120.0;
$client->maximumRetryCount = 2;
```

`extraBody` overrides built-in body fields on collision. For `OllamaClient`, its entries are written inside the native `options` object, where runner settings such as `num_ctx` belong.

### Anthropic prompt caching

Prompt-prefix caching is opt-in and belongs to `AnthropicClient`, not the agent loop:

```php
/** @var AnthropicClient $client */
$client->cachePromptPrefix = true;
```

The client adds a five-minute `ephemeral` breakpoint to the last generated tool descriptor and converts non-blank system text into a marked text block. The tools breakpoint allows that catalogue to be reused even when the system prompt changes. Tool order, schemas and message contents are preserved; messages are not marked by this option. Empty catalogues and blank or absent system prompts do not create cache blocks.

`extraBody` remains authoritative. A supplied `system` or `tools` field replaces that generated field, including its cache markers, without being rewritten. For automatic caching of the growing conversation, leave `cachePromptPrefix` disabled and use the provider's top-level option instead:

```php
$client->extraBody["cache_control"] = ["type" => "ephemeral"];
```

The automatic option may also be combined with prefix breakpoints. Applications supplying custom block markers or TTLs must respect Anthropic's breakpoint count and TTL-ordering rules. Cache eligibility, minimum prompt size and expiry are provider-specific; a marker does not guarantee a hit. See [Anthropic prompt caching](https://platform.claude.com/docs/en/build-with-claude/prompt-caching).

Anthropic input usage is normalized as `input_tokens + cache_creation_input_tokens + cache_read_input_tokens`, whether caching was enabled through this option or through `extraBody`. These tokens all count toward run budgets and trace totals. The nested `cache_creation` TTL breakdown is not added again. These totals measure tokens, not money: cached input has different billing rates, and the runtime does not calculate cost or expose separate cache-hit counters.

## Building the in-process tool catalogue

`LLMResponder` already exposes protected `$descriptor` and `$registry` properties. A responder subclass can pass `$this->registry` directly to `LLMAgent`; override `$restrictedTools` to remove tools from every surface that reads that catalogue.

Outside a responder, build the same catalogue from the managed-object context:

```php
use Sabatier\Service\MCP\Schema\AttributeSchemaFactory;
use Sabatier\Service\MCP\Schema\ModelDescriptor;
use Sabatier\Service\MCP\Schema\ModelSchemaExtractor;
use Sabatier\Service\MCP\Schema\PredicateGuideFactory;
use Sabatier\Service\MCP\Schema\SchemaLocalizer;
use Sabatier\Service\MCP\Schema\VocabularyRepository;
use Sabatier\Service\MCP\ToolResolver;
use Sabatier\Service\MCP\Tools\ToolRegistry;

$descriptor = new ModelDescriptor(
    new ModelSchemaExtractor($context, new AttributeSchemaFactory()),
    new VocabularyRepository(),
    new SchemaLocalizer(),
    new PredicateGuideFactory(),
);
$registry = new ToolRegistry(new ToolResolver($context, $descriptor)->resolve());
```

The registry includes built-in and application-defined MCP tools. Tool-level RBAC, ownership, row and field checks still run in-process; the agent policy below adds a separate approval boundary around side effects.

## Budgets and write approval

The default `LLMExecutionPolicy` permits at most 64 tool calls and eight subagent launches, and denies every state-changing tool call. A model cannot approve its own write. Supply a closure only after the application has obtained approval for the concrete operation:

```php
use Sabatier\Service\LLM\LLMExecutionPolicy;
use Sabatier\Service\LLM\LLMToolCall;

$policy = new LLMExecutionPolicy(
    maxToolCalls: 16,
    maxSubagentCalls: 0,
    maxInputTokens: 50_000,
    maxOutputTokens: 8_000,
    maxTotalTokens: 58_000,
    writeApproval: fn(LLMToolCall $call): bool =>
        $call->name === "create" && $call->arguments["entity"] === "Draft",
);

$agent = new LLMAgent(
    $client,
    $registry,
    canSpawnSubagents: false,
    timeLimit: 30.0,
    executionPolicy: $policy,
);
```

Budgets, the monotonic deadline and write approval are shared with every child run. Set both `canSpawnSubagents: false` and `maxSubagentCalls: 0` when delegation is not part of the product surface.

## Handling run endings

Treat `isComplete` as the success check and `stopReason` as the recovery instruction. Partial text from an incomplete run is not a completed answer.

| Stop reason | Typical caller response |
|-------------|-------------------------|
| `done` | Persist and return the final assistant message. |
| `iterationCap` | Raise the turn cap only after checking for a loop. |
| `deadline` | Retry only if the caller can grant a larger execution window. |
| `providerFailure` | Inspect `isRetryable`; do not retry invalid credentials or requests. |
| `toolProviderFailure` | Restore the remote tool service; inspect `isRetryable`. |
| `outputLimit` or `refusal` | Do not present the partial response as completion. |
| `toolCallLimit`, `subagentCallLimit` or a token limit | Ask for a narrower task or grant an explicit larger budget. |
| `writeApprovalRequired` | Obtain user approval for that concrete call, then start a new run with a matching policy. |
| `contextLimit` | Increase the context limit or use compaction/retrieval. |

## Context windows and retrieval

`WindowedLLMContextAssembler` drops complete old conversation turns while preserving system messages and the newest turn. Its default size measurement is approximate UTF-8 bytes; provide a `measure` closure when the provider's tokenizer is available.

```php
use Sabatier\Foundation\ArrayClass;
use Sabatier\Service\LLM\WindowedLLMContextAssembler;

$context = new WindowedLLMContextAssembler(
    maximumMessages: 40,
    maximumSize: 96_000,
    compressor: fn(ArrayClass $omitted): string => summarize($omitted),
);
```

`RetrievalAugmentedLLMContextAssembler` decorates any assembler with an application-supplied `LLMRetriever`. Retrieval runs for each assembly against the latest non-empty user message, bounds document count and byte size, preserves provenance, and inserts retrieved text as explicitly untrusted evidence rather than system instructions.

```php
use Sabatier\Service\LLM\RetrievalAugmentedLLMContextAssembler;

$context = new RetrievalAugmentedLLMContextAssembler(
    $retriever,
    new WindowedLLMContextAssembler(maximumMessages: 40, maximumSize: 96_000),
    maximumDocuments: 8,
    maximumSize: 32_768,
);
```

A retrieval failure propagates by default. A product where retrieval is optional should encode that policy in its retriever by returning an empty `ArrayClass` when degradation is acceptable.

## Remote MCP tools

Pass an `MCPToolExecutor` instead of a `ToolRegistry` to keep the model loop unchanged while tools execute in another process. Remote descriptions and MCP annotations are not trusted effect metadata: every call is treated as state-changing and non-cacheable unless the application supplies concrete `readOnly` and `cacheable` classifiers. `MCPClient` retains the optional annotations on `ToolDescriptor` for inspection, but `readOnlyHint` and `idempotentHint` never bypass those classifiers. See [Tool annotations](MCP.md#tool-annotations).

The bundled `MCPClient` uses the stateful 2025 handshake lifecycle documented in [MCP.md](MCP.md#protocol-compatibility). The remote server must support one of those revisions.

## Observability

An `LLMRunObserver` receives immutable run, context, provider-turn and tool-call events. The default `bestEffort` failure policy logs observer failures and allows the run to continue; use `LLMRunObserverFailurePolicy::strict` only when losing telemetry must abort the operation.

Do not reconstruct completion from events. `LLMRun` remains the authoritative outcome, including provider/tool failure normalization and all shared-budget terminal states.
